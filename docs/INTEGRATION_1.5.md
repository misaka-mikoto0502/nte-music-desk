# 1.5 开发版统一检查

2026-10-30。桌面窗口为默认入口，浏览器为手动兼容入口；两者不维护各自的识别或保存算法。

## 当前已整合

| 内容 | 共同实现与证据 |
| --- | --- |
| CPU 加速与兼容回退 | 同一个 worker.js；真实缺失 WASM 的 WebView2 完整流程已回退到 JS CPU，不依赖假引擎 |
| 选段、预设、解码与保存 | pipeline.js 共用文件验证、时长/片段、散列、解码、重采样、识别、提交与取消；窗口自检也直接调用它 |
| 进度和剩余时间 | 页面统一接收真实推理事件，使用同一个 ETA 实现；加载/保存阶段不伪造秒数 |
| 自动保存与下载 | 工作台副本先持久化，再提供固定下载链接；实测下载 MIDI 与工作台副本逐字节一致；同名下载不覆盖旧文件 |
| 弱音与和弦起音 | 预设和 24ms 对齐通过同一请求进入后端；保留对齐前文件，默认仍是均衡识别与原起音 |
| 结果说明 | 显示候选/当前/对齐音数；可下载候选谱与对齐前谱；候选明确标注可能含误判，不当作正确音符总数 |
| 任务协调 | 轻量、高级处理与游戏演奏共用任务锁；高级窗口提前打开后也不能越过轻量任务检查 |
| 主窗口布局 | 加高拖入区，曲目区仅保留曲目架；旧历史字段兼容保留，不删用户文件 |
| 分栏布局 | 最终结果页面在 1280×720、1000×650、900×600 三种 CSS 视口中实际检查：无文档滚动、无面板溢出、下载可见、页脚不遮挡 |

高级分离、MuScriptor/GAME 仍是本工作台内的可选独立引擎，并非默认拖入流程。它们共用任务协调、结果导入和演奏后端，不把重型依赖塞进轻量包。

## 本轮补完的真实验证

- arpeggio：共用流程生成 20 音，持久化、下载、恢复结果入口通过。
- triads：同一份 WAV 经 WebView2 加速与缺失 WASM 的 CPU 回退均生成 16 音，两份 MIDI 字节完全相同。之前与 Node PCM 的 15 音差异不能作为两个后端的差异；输入/解码路径不同，不能混用基准。
- 弱音预设＋24ms 起音对齐：共用流程生成 28 音，处理记录、对齐前 MIDI 与候选文件都保留。此数量不是质量提升结论。
- 真正执行首个推理窗口后取消：任务解除忙碌，不生成半成品 MIDI。
- 三种最终结果页尺寸均由实际 WebView2 DOM 几何核对，没有通过隐藏溢出伪造通过。
- 同一次操作只使用一份参数快照；保存阶段禁止页面取消，保存已完成时保留结果，避免用户误以为已保存文件被撤回。

开发者复现入口为 tools/check_audio_window.py；支持 --without-wasm、--profile、--align 和 --cancel。测试仅用本地自制短句，临时窗口在屏幕外运行，不向游戏或其他应用发送输入；测试音频与结果不进入 Git。

## 仍需区分的边界

1. 漏音不能等同于候选数与当前数的差值。宽松预设在已有短句中增加了误判，故不替换默认设置。原曲声部、单旋律、音域折回与游戏发声限制需要分层判断。
2. 独立钢琴的混合黑白键依赖全局 Shift，仍采用约 55ms 分组；吉他钢琴模式没有该分组。不能声称两者都已严格同时发声。
3. 使用者已准备钢琴界面，并提供 Esc → 等待 → G → 钢琴键模式的吉他切换路径。但 Windows 返回新整合包的权限请求已取消，未产生新包的游戏演奏任务，本轮没有发送音符。完整悬浮窗操作、物理 F7/F8、12–36 音实际发声数和钢琴绝对音高仍需实听，不能把旧包悬浮窗或软件报告算成新包验收。
4. 用户已确认主窗口的 MIDI/音频拖入和正常 UAC 启动；独立转谱窗口的新操作体验仍可继续收集反馈。
5. 更换音色、波形编辑、局部改谱/撤销属于后续规划，不把历史计划当成本轮已完成事项。

源码打包工具已同步识别明确列出的窗口宿主与 SDK 组件，保留 .gitattributes；不将 node_modules、个人配置或运行记录写入源码 ZIP，也不默认覆盖已有发布包。当前版本保持为 1.5 开发版。
