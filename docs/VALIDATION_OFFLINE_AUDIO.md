# 离线转谱验证与开发记录

验证日：2026-11-08 至 2026-11-09。以下保留离线开发预览的原始测试条件和记录，已由使用者确认整合为 2.0.2；正式包检查见 [VALIDATION_2.0.2.md](VALIDATION_2.0.2.md)。全部基于同一 `release/2.0.0` 工作区，不覆盖旧版标签及附件。以下区分识别质量、接口一致性和程序运行，不能相互代替。

## 评测口径

使用 mir_eval 0.8.2。Note F1 同时要求音高误差不超过 50 cents、起音误差不超过 50ms；带结束时间的 F1 另要求误差不超过 `max(50ms, 参考时长的20%)`。不寻找最佳移调，不手工移动预测来提高评分。旋律 RPA 使用有声参考帧的 50 cents 音高容差，不等同于完整音符准确率。汇总为逐样例宏平均。

## 钢琴

六组有已知 MIDI 的合成短句：音阶、琶音、重复音、三和弦、连奏、力度变化。音色来自既有 CC0 VSCO2 CE 测试音色。新模型与此前已保存的 Basic Pitch 输出比较，参考谱不变。

| 引擎 | Note F1 | 带结束时间 F1 |
|---|---:|---:|
| 原 Basic Pitch 均衡版 | 83.23% | 74.05% |
| Transkun 2 ONNX | 98.72% | 69.71% |

新方案三和弦参考 16 音，预测 16 音，起音音高 F1=100%；力度变化参考 12 音，预测 14 音，是仍存在的误音案例。结束时间评分没有全面领先，不能隐藏这个退步。合成音色包络与真实钢琴释放存在差异；还需真实钢琴曲与听感验收。不能把这六条简单短句的 98.72% 宣传为任意钢琴曲准确率。

另对 TuesdayCrowd/audio-claudio 的 21.8 秒 `two-bar-x4` 跨片段样例进行端口一致性验证：35 个有音高预测，对固定的原生 Transkun 结果，Note F1 与带结束时间 F1 均为 100%。这证明此样例上的前端、解码与接缝实现一致，**不是**对真实演奏的 100% 准确率。

## 人声与含伴奏歌声

使用 [vocadito v3](https://zenodo.org/records/5578807)（Bittner 等，2021，CC BY 4.0）按编号选定前三段，不在跑分后挑选样例。该数据为真实独唱，有两位标注者的音符标注及帧级 f0，语言为 Tagalog、Spanish、Tagalog。

| 方法 | 对标注者1的 Note F1 | 对标注者2的 Note F1 | 旋律 RPA |
|---|---:|---:|---:|
| 仅 MuScriptor small | 46.25% | 55.45% | 不以多音输出计算单旋律 RPA |
| GAME small 独唱 | 62.97% | 74.51% | 80.67% |
| GAME small，混入钢琴伴奏 | 47.07% | 50.28% | 69.39% |

混音使用同一组三段真实人声，加既有 CC0 琶音伴奏，人声／伴奏整体 RMS 为 +6.02dB。预测未人工修调；没有先分离人声。这是可重复的受控混音，不代表商业流行歌曲的平均效果，也不代表 GAME＋MuScriptor 合并所有音轨的整体 F1。歌曲流程将 GAME 的旋律单列音轨，其他声部单独保留，便于试听和人工选轨。

GAME 的 D3PM 导出图包含 RandomUniform 操作。每个任务在创建会话前固定种子为 0；上表以每条样例各自新建会话重测。相同 15 秒混音在两个全新会话中输出完全相同的 25 个演唱事件，独立冻结包另核对与源代码的旋律事件一致。未固定种子的初测数据另行保留，不与最终数据混用。

结论：专用歌声模型明显优于只用多乐器模型，但人声混音仍存在错误、滑音半音化和音符边界问题。当前达到基础可试用能力，不能承诺所有歌曲“听起来与原曲一样”。未来改善人声分离和真实完整混音评测，应保留相同样例和指标比较。

## 程序与打包验证

### CPU 性能修复与一致性复测

在 Ryzen 7 7745HX（8 核／16 线程）上，以使用者认可的一次完整歌曲结果作为回归基准。曲长 288.301 秒，基准最终 MIDI 为 1,933 音；原始多乐器输出 1,983 个事件，歌声输出 402 个事件。原文件及商业录音不提交仓库。原流程根据请求及结果文件时间记录共 635.61 秒，其中多乐器阶段 586.88 秒。

定位到 Windows MSVC `/arch:AVX` 不会定义 `__F16C__`，ggml 的 F16 向量转换分支因此没有启用。现于已经要求 AVX/F16C 的 CPU 后端显式启用硬件转换，仍由基线指令集入口检查 CPUID 与操作系统 AVX 状态；保留原 F16 权重、音频分段、解码和后处理。整首原生阶段实测 101.75 秒，1,983 个事件文件的 SHA-256 与基准完全一致。8／4／2 线程的同一 30 秒片段分别为 6.63／8.74／14.28 秒，默认上限维持 8 线程。

首次完整源码任务为 163.88 秒，包含校验、两次解码、歌声识别、伴奏识别、整理、MIDI 和两份对照试听。歌声、伴奏、合并事件和最终 MIDI 均与基准逐字节一致。此结果早于后续歌声内存优化：关闭五个顺序模块的独立 CPU 内存池缓存和空闲线程自旋，最多使用半数逻辑核、上限 8 线程。完整歌声单独复测为 57.34 秒，峰值工作集 408,076,288 字节，402 个事件仍完全一致；此前完整源码工作进程的峰值为 1,199,742,976 字节。

**最终完整 Windows 便携包复测为 155.516 秒（约 2 分 36 秒），通过 180 秒门槛**，总等待比原任务缩短约 75.5%。其中歌声阶段 56.656 秒、伴奏阶段 96.254 秒，包含其余校验、解码、保存和试听准备。所有歌声、伴奏、合并原始事件文件及最终 MIDI 与认可的基准逐字节一致。工作进程峰值工作集 414,433,280 字节，独立伴奏进程峰值 495,607,808 字节；两个数是各进程峰值，不能直接相加当作同时占用。测试只保留 System32 PATH，关闭在线模型访问，不使用外部 Python／解码器。Windows ZIP 为 355,418,234 字节，模型权重及精度不变，包体积基本维持原状。

这些一致性比较证明本样例的优化没有改变既有输出，不能当作对人工标注的识别准确率。3 分钟门槛以完整便携包的任务墙钟时间验收，不能用片段速度外推；不同 CPU、电源状态、并发负载、曲长和音符密度仍会影响耗时。没有使用 RTX 4060，也没有增加 GPU、CUDA 或模型下载依赖。

复测命令（本机路径替换为自己的文件）：

```powershell
python tools/verify_offline_audio.py --exe "应用目录/异环演奏工作台.exe" --source "录音.mp3" --profile song --work .build/validation/performance --baseline-job "已认可的任务目录" --max-seconds 180
```

具体计时、各进程峰值内存、原始预测、一致性及验收结果保存在 `.build/validation/performance/`。`result.json` 新增逐阶段耗时和实际后端；便携包校验额外保存完整墙钟时间。构建资源暂存采用自动清理的临时目录，独立解压验证默认只保留报告和小型结果；需要调试副本时显式使用 `--keep-extracted`。取消任务后只清理本次 PCM 与未完成文件，保留用户音频、已保存曲谱及原始预测记录。

最终 144 项源码单元检查通过；完整包三和弦样例仍为参考／预测各 16 音，mir_eval 起音音高 P／R／F1 均为 1.0。真实歌曲任务在歌声识别阶段取消后，工作进程退出，PCM 文件被清理，状态为 cancelled。独立中文及空格目录解压、自检、片段导出、资源不变和 ZIP 校验全部通过；成功后自动移除第二套解压应用。未发送游戏按键。

自动化回归覆盖：导入路由、原调和弦与力度保留、多音轨、重复音去重、原始记录不变、取消后晚到结果不导入、只扫描完整成功任务、Windows 进程树终止、历史曲目改名／隐藏与源码包过滤。原生界面的选段展开曾挤压底部按钮，已改为底部优先保留空间、随内容调整窗口。

真实源代码子进程已跑通钢琴和歌曲样例的解码、推理、原始事件、MIDI、对照 WAV 与最终记录。独立 Windows 包另外执行 `verify_release.py` 和 `verify_offline_audio.py`，检查完整资源、独立解压、只读安装目录、系统 PATH、不依赖外部 Python／FFmpeg、关闭在线模型访问及真实模型推理。具体完成状态和体积见开发预览目录内的 JSON 验证报告；未通过的包不作为完成品提供。

## 后台转谱与播放并行验证

原生本地转谱使用独立进程和低于普通的 Windows 调度优先级（BELOW_NORMAL_PRIORITY_CLASS）；主窗与迷你播放器保持可用，旧轻量／高级引擎仍互斥。完成时保护当前演奏、试听、对照试听窗口及等待期间另选的曲目；用户选择“后台运行”后仅加入曲目列表。取消转谱和停止演奏使用各自的进程树、控制文件与消息队列。

155 项源码检查通过，新增覆盖互斥边界、前后台启动、完成不切曲、隐藏及重开进度窗口、拒绝第二个转谱、暂停／跳转／停止隔离和子进程低优先级继承。`tools/verify_background_audio.py` 使用真实模型、真实 Tk 窗口控制路径和独立播放调度子进程，键盘替换为不发送系统输入的记录后端；验证取消真实转谱不终止播放、真实试听文件可在转谱时生成、暂停／跳转／继续可用、完成不切换曲目、停止后所有模拟琴键释放。

与既有 288.301 秒歌曲基准对照：后台完整源码任务 153.884 秒，最终 1,933 音符；歌声、伴奏、合并事件和 MIDI 均逐字节一致。并行 60 秒、3,000 个每隔 20ms 的真实调度事件，记录后端的延迟中位数 0.330ms、99 百分位 0.683ms、最大 2.249ms。结果保存在 `.build/validation/background-playback/`。没有向游戏发送按键，这些指标不能当作游戏音色、实际发声延迟、焦点行为或所有低配电脑下无影响的实机验收。


## 演奏启动与迷你播放器联动

点击开始演奏后，由演奏进程请求恢复／聚焦已核对的游戏窗口，确认前台归属后向主界面发送 `game_focused` 进度。主界面只在成功确认时自动显示一次迷你播放器；零倒计时也通过 playing 进度携带同一确认。启动时不提前显示小窗，上次隐藏偏好不阻止下一次演奏自动显示；本次关闭后不反复弹出。原生显示使用 SW_SHOWNOACTIVATE 和 SWP_NOACTIVATE，避免 Tk deiconify 抢焦点。电脑试听仍不切换到游戏。

新增回归覆盖恢复最小化窗口、确认聚焦顺序、系统拒绝切换／取消／窗口变化时不发送按键、零／非零倒计时、主窗自动显示、同次不重复弹出、下一次重新显示与电脑试听边界。真实 Windows 原生窗口检查确认显示／隐藏／重显可用，显示小窗时前台句柄保持不变。焦点切换与演奏流程使用模拟游戏后端，未向真实游戏发送按键；实际游戏自动切换及独占全屏覆盖仍需实机验收。

## 2026-11-09 当前版本整理与场景复核

源码仍仅在 `release/2.0.0` 的一个工作区开发，应用版本维持 2.0.1，构建标识为 `offline-preview`；公开标签与历史附件不修改。README 与 CHANGELOG 已补齐本地模型、性能优化、后台转谱、状态清空、曲目整理、自动小窗、明音进度和下拉换曲，明确区分当前预览与已发布快照。构建及验证路径统一到 `.build/current`、`.build/cache`、`.build/validation`。

- 转谱期间先换到 B 曲再回到 A 曲，原来只比较最终路径，仍可能自动载入结果覆盖用户选择。现在记录选曲变化次数，完成时只入库，保留当前曲目。
